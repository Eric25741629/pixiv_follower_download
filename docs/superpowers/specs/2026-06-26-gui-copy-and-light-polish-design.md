# GUI 用語一致化與輕量視覺整理規格

日期：2026-06-26
狀態：已與使用者確認方向，本文為實作前 spec
取代：`docs/superpowers/specs/2026-06-26-settings-taxonomy-redesign-design.md`

## 目標

把目前 GUI 從「各頁各寫各的」整理成一套一致的使用者語言與輕量視覺規則，讓整個 app 在以下三件事上更穩定：

1. **用語一致**：同一件事在不同頁面、按鈕、對話框、Snackbar、執行記錄中，不再用不同說法。
2. **理解成本更低**：保留必要技術詞，但標題、欄位、提示與執行訊息都先講用途，再帶術語。
3. **資訊權重更清楚**：重要狀態、主要操作、次要說明、空狀態與錯誤訊息的顯示層級一致，不再互相搶注意力。

這次工作包含：

- 四個主頁面的固定文案
- 設定頁分類與欄位文案
- 對話框 / 確認框 / Snackbar / 狀態提示
- `即時 Log` 內的執行過程訊息
- 小幅 UI polish（間距、資訊權重、局部排列、狀態顯眼度）

這次工作**不包含**重新設計整體 UI 架構或重新定義功能流程。

## 已確認的範圍決策

1. 不只整理設定頁，而是整理 **全 GUI**。
2. 範圍包含固定 UI 文案，也包含 **執行中動態訊息**。
3. 用語風格採 **技術詞保留，但更白話**。
4. 視覺改動等級為 **小幅 UI polish**：
   - 可以調整間距、資訊權重、面板內容排列、按鈕文字與狀態顯眼度
   - 不改主導航、不重做 glass theme、不改頁面架構

## 現況問題

目前 GUI 的不一致，主要有五類：

1. **混用中英文且沒有規則。**
   例如 `Cookies`、`即時 Log`、`Task failed`、`Pending URL`、`total following`、`統計資料` 同時存在。
2. **同層級元件的語氣不同。**
   有些按鈕偏口語（`一鍵執行`），有些偏工程詞（`PID 模式`），有些是直譯（`Cookies`）。
3. **固定文案和執行訊息像是兩套語言。**
   設定頁與主頁較偏繁中說明，但執行記錄仍殘留大量英文或過短的工程訊息。
4. **資訊權重不穩。**
   重要的狀態和次要說明有時看起來差不多，空狀態、警告、錯誤與完成訊息也沒有一致規則。
5. **設定頁分類邏輯與其他頁面不對齊。**
   設定頁先前最大問題是欄位混類；即使單獨修好，如果不和全 GUI 的用語系統一起整理，仍會回到局部一致、整體不一致。

## 受眾與語氣

目標受眾不是完全非技術使用者，而是：

- 願意自己管理 Cookie / Proxy / User-Agent 的使用者
- 能接受 `PID`、`JXL`、`Cookie` 這類術語
- 但不希望每個頁面都像在讀內部 debug 訊息

因此，文案基調採：

- **保留術語**：Cookie、Proxy、User-Agent、PID、JXL、R-18、R-18G、AI
- **用途優先**：先說這個東西做什麼，再提術語
- **句子縮短**：避免又長又像註解的說明
- **結果先行**：執行訊息先說成功 / 失敗 / 略過，再補原因

## 非目標

- 不重做 liquid glass 視覺系統
- 不新增新的導航層級或設定分頁
- 不改 `SettingsStore` schema
- 不改 `WorkerEvent` 事件模型
- 不做 i18n 系統抽離
- 不要求所有 core thread 訊息都抽成統一 message factory
- 不改任何實際下載、排程、Cookie 配對、統計計算邏輯

## 全域文案規則

### 1. 名稱層級

- **頁面名稱**：用中文主詞，必要術語作補充，不直接拿英文複數當頁名
- **區塊名稱**：用「主題名詞」，不寫成完整句
- **按鈕名稱**：用「動作 + 對象」
- **說明文字**：先講用途，再講限制或影響
- **動態訊息**：先講結果，再講對象或原因

### 2. 術語保留規則

保留以下術語原文：

- `Cookie`
- `Proxy`
- `User-Agent`
- `PID`
- `JXL`
- `R-18`
- `R-18G`
- `AI`
- `HTTP`

規則：

- 可以保留術語，但不要單獨拿術語當整個區塊標題，除非該區完全圍繞該術語
- 英文術語前後要用中文句子包住，不直接丟工程字串給使用者

### 3. 避免用語

下列字眼不應再直接出現在使用者可見 UI：

- `Task failed`
- `total following`
- `Pending URL`
- `URL階段開始` 這種缺空格且未說明對象的訊息
- 純 debug 風格的欄位名，如只剩 `PID progress`

### 4. 狀態句模板

所有執行訊息優先使用以下模板：

- **開始**：`開始 <動作>：<對象/數量>`
- **進行中**：`<動作>中：<對象/進度>`
- **完成**：`<動作>完成：<摘要>`
- **略過**：`略過 <對象>：<原因>`
- **失敗**：`<動作>失敗：<原因>`
- **重試**：`重試 <對象>：第 X/Y 次，原因：<原因>`
- **警告**：`注意：<情況>`

## 用詞字典（最終優先）

這一節是整份 GUI 文案的最高優先字典。後續若頁面既有文字與這一節衝突，以這一節為準。

### 1. 核心名詞

- `作者`
  - 定義：Pixiv 上的創作者，作為追隨、掃描與分組下載的來源單位
  - 用法：頁面與訊息中預設使用 `作者`
  - 避免：在同一個 GUI 裡交替使用 `畫師`、`作者`
- `作品`
  - 定義：以一個 `PID` 為單位的單一作品
  - 用法：篩選、下載、略過、失敗、完成摘要都以 `作品` 為主語
- `作品頁數`
  - 定義：同一個 `PID` 底下的頁面數
  - 用法：用在單作品多頁進度
  - 避免：單獨把它叫成 `分頁` 或 `本作分頁`
- `收藏`
  - 定義：使用者在 Pixiv 上按愛心或加入收藏的作品來源
  - 用法：GUI 一律用 `收藏`
  - 避免：使用者可見文字中混用 `書籤`
- `Cookie`
  - 定義：登入會話憑證
  - 用法：保留原文 `Cookie`
- `Proxy`
  - 定義：請求使用的代理連線
  - 用法：保留原文 `Proxy`
- `User-Agent`
  - 定義：瀏覽器識別字串
  - 用法：保留原文 `User-Agent`
- `PID`
  - 定義：作品 ID
  - 用法：在需要精準定位作品時保留 `PID`
- `JXL`
  - 定義：JPEG XL 轉檔功能
  - 用法：保留原文 `JXL`
- `執行記錄`
  - 定義：主頁內顯示執行過程的即時訊息區
  - 用法：GUI 一律用 `執行記錄`
  - 避免：`即時 Log`
- `執行統計`
  - 定義：摘要與累積數據頁面
  - 用法：頁面標題一律用 `執行統計`
  - 避免：`統計資料`
- `Cookie 管理`
  - 定義：Cookie 維護頁面
  - 用法：頁面標題一律用 `Cookie 管理`
  - 避免：`Cookies`
- `全部步驟`
  - 定義：一次執行步驟 1 到步驟 4 的使用者語言
  - 用法：按鈕、排程與提示文字中都用 `全部步驟`
  - 備註：程式內部識別仍可保留 `Run All` / `run_all`

### 2. 核心動詞

- `抓取`
  - 定義：從 Pixiv 或相關來源取得作者、收藏或清單資料
- `掃描`
  - 定義：逐一展開作者或作品，建立待處理名單
- `整理`
  - 定義：把中介資料轉成下一步要處理的結果，例如 URL 清單
- `下載`
  - 定義：把作品檔案寫入磁碟
- `轉檔`
  - 定義：下載後轉成 JXL
- `測試`
  - 定義：驗證 Cookie 或 Proxy 是否可用
- `啟用`
  - 定義：使用者明確允許系統使用某個資源
- `停用`
  - 定義：使用者明確禁止系統使用某個資源

### 3. 狀態用語

- `有效`
  - 定義：測試通過，可使用
- `失效`
  - 定義：測試失敗或已不可用
  - 備註：`失效` 是系統判定，不等於使用者手動 `停用`
- `測試中`
  - 定義：正在驗證可用性
- `未知`
  - 定義：尚未測試或沒有足夠資訊判定
- `開始`
  - 用於階段或動作啟動
- `進行中`
  - 用於持續中的狀態
- `完成`
  - 用於階段結束
- `成功`
  - 用於完成摘要中的成功計數，不拿來當整個階段標題
- `失敗`
  - 用於動作未完成且需要說明原因
- `重試`
  - 用於再次嘗試
- `已暫停`
  - 用於任務已進入暫停狀態
- `已繼續`
  - 用於任務從暫停恢復
- `已停止`
  - 用於任務已停止

### 4. 容易混淆的詞

- `跳過` vs `略過`
  - `跳過`：用在設定說明或功能描述，表示「遇到某條件時不處理」
    - 例：`作品沒有 tag 時跳過`
  - `略過`：用在執行記錄，表示「這次實際沒有處理」
    - 例：`略過 PID 123456：未達最低讚數`
- `停用` vs `失效`
  - `停用`：使用者主動關閉
  - `失效`：系統測試後判定不可用
- `完成` vs `成功`
  - `完成`：一個步驟或一個階段結束
  - `成功`：完成摘要中的成功數量
- `作者` vs `畫師`
  - GUI 預設統一用 `作者`
  - 若需要對齊既有資料結構或 tooltip，可在次要說明中提及 `畫師`，但不作為主要標籤

## 輕量視覺整理規則

這次只做「視覺整理」，不做視覺重設計。

### 1. 資訊權重

- 頁面標題只保留一個主要標題，不再讓次標、計數、功能按鈕看起來像同層
- 區塊說明統一用較淡字色與較短段落
- 主要操作按鈕保持唯一主色，其餘次要操作維持次要樣式
- 警告 / 停止 / 失敗狀態用固定語意色，不和一般說明共用權重

### 2. 間距與密度

- 頁面標題、工具列、主要內容區之間留固定垂直節奏
- 同一列內只放同類操作；不把頁面標題、計數、批次動作全部擠成一條沒有層次的長列
- 區塊內 `subhead` 與表單控件之間縮短距離，區塊與區塊之間維持較大距離

### 3. 排列微調

- 允許把過於擁擠的 header action 列拆成上下兩層
- 允許調整資訊卡或工具列中控制項的前後順序，只要不改功能結構
- 允許把次要資訊（例如補充說明、上次檢查時間、數量統計）移到更明確的輔助位置

## 全域名稱對照

這些是本 spec 明確要求改掉的高可見度名稱：

- `Cookies` -> `Cookie 管理`
- `統計資料` -> `執行統計`
- `即時 Log` -> `執行記錄`
- `一鍵執行` -> `執行全部步驟`
- `測試選取` -> `測試選取項目`
- `啟用選取` -> `啟用選取項目`
- `禁用選取` -> `停用選取項目`
- `自動配對` -> `自動配對 Proxy`

## 各頁規格

### A. 主頁（MainView）

#### 目標

讓主頁看起來像「執行控制台」，不是把模式、步驟卡、進度條與 log 並排堆在一起。

#### 固定文案

- 主要操作按鈕：
  - `一鍵執行` -> `執行全部步驟`
  - `暫停` 保留
  - `停止` 保留
- Log 區標題：
  - `即時 Log` -> `執行記錄`
- 模式列：
  - `來源` 保留
  - `抓追隨` -> `追隨作者`
  - `抓收藏` -> `我的收藏`
  - `追隨範圍` 保留
- 進度名稱：
  - `整體進度` 保留
  - `本作分頁` -> `目前作品頁數`

#### 顯示整理

- `模式列`、`執行按鈕列`、`進度區` 要維持清楚的上下分層
- `phase` 行與 `progress/meta` 行的權重要分開：
  - phase 用來說「現在在做哪一步」
  - progress/meta 用來說「做到哪裡」
- `執行記錄` 區標題與 log 本體之間留固定小間距，避免像同一塊文字牆

### B. 設定頁（SettingsView）

設定頁沿用並吸收先前 settings-only spec，主區塊改為以下 8 區：

1. `帳號與登入`
2. `連線與瀏覽識別`
3. `作品來源與抓取策略`
4. `下載位置與資料夾分類`
5. `檔名與時間戳`
6. `標籤整理與缺值處理`
7. `作品篩選條件`
8. `格式轉換、效能與自動化`

#### 設定頁重點文案調整

- `無 tag 不下載` -> `作品沒有 tag 時跳過`
- `無時間不下載` -> `作品沒有發佈時間時跳過`
- `邊查邊下（查到即下載，合併步驟三、四）`
  -> `查到即下載（合併步驟 3、4）`
- `邊查邊下並發數（1=循序）`
  -> `同時處理作品數`
- `強制重新掃描全部畫家（忽略30天，一次性）`
  -> `下次掃描時忽略 30 天跳過規則（一次性）`
- `單帳號冷卻秒數`
  -> `每個帳號的冷卻秒數`
- `單執行緒 PID 模式`
  -> `以單執行緒處理作品`

#### 顯示整理

- 每個主區塊都要有一句用途說明
- `JXL 轉檔` 從輸出類區塊拆出，不再和路徑 / 檔名規則混在一起
- 缺值處理與檔名 tag 整理獨立成一區，不再掛在「下載輸出」之下

### C. Cookie 管理頁（CookiesView）

#### 目標

讓這頁看起來像「Cookie 與 Proxy 維護台」，而不是一列標題後面塞滿所有批次動作。

#### 固定文案

- 頁面標題：
  - `Cookies` -> `Cookie 管理`
- 主要按鈕：
  - `+ 新增` -> `新增 Cookie`
  - `測試選取` -> `測試選取項目`
  - `測試全部` 保留
  - `啟用選取` -> `啟用選取項目`
  - `禁用選取` -> `停用選取項目`
  - `自動配對` -> `自動配對 Proxy`
- 對話框標題：
  - `新增 Cookie` 保留
  - `編輯 Cookie` 保留

#### 顯示整理

- `標題 + 數量摘要` 應與 `批次操作按鈕列` 分層，不必硬塞成同一列
- `全選` checkbox 保留，但視覺上應屬於批次操作區，而不是頁面標題的一部分
- 每列 Cookie 資訊維持三段：
  - 選取 / 啟用狀態
  - 別名 / 狀態 / 上次檢查
  - Proxy 綁定 / 編輯 / 刪除
- `檢查：xx` 文案可保留，但若調整，方向應是更自然的時間語氣，例如 `上次檢查：剛剛`

### D. 統計頁（StatsView）

#### 目標

讓統計頁更像「可讀的摘要」，不要只是一組數字卡片加一個圖表標題。

#### 固定文案

- 頁面標題：
  - `統計資料` -> `執行統計`
- 模式切換：
  - `本次執行` 保留
  - `歷史累計` 保留
- 圖表區標題：
  - `Cookie 請求次數` -> `各 Cookie 請求次數`
- 空狀態：
  - `尚無資料` -> `目前沒有統計資料`

#### 統計卡片名稱

以下名稱保留，但整體語氣要一致：

- `總下載流量`
- `JXL 節省空間`
- `HTTP 請求數`
- `執行時間`

#### 顯示整理

- 模式切換與卡片群之間留清楚段落，不要像附屬按鈕
- 空狀態不只顯示一行字，應放在對應區塊中心或穩定位置，不和正常資料版面混雜
- `Cookie 請求次數` 圖表若沒有資料，空狀態應與卡片區一致

## 對話框、Snackbar、狀態提示規則

### 1. 對話框

- 標題一律先說事件，再說條件
- 確認框避免過長技術警告句，改成：
  - 第一行：說明風險
  - 第二行：說明後果

例如：

- `冷卻時間偏短`
  內文改為：
  `每個帳號的平均冷卻時間低於建議值 30 秒。`
  `這可能提高被 Pixiv 風控偵測的風險，仍要套用嗎？`

### 2. Snackbar

- 成功訊息避免只寫「已儲存」這種太抽象的句子
- 方向：
  - `設定已儲存` 可保留
  - 如果未來需細分，採 `已儲存 <對象>`，例如 `已儲存設定`

### 3. 狀態標籤

- Cookie 狀態只使用：
  - `有效`
  - `失效`
  - `測試中`
  - `未知`
- 不再混入別的同義詞，例如 `正常`、`可用中`、`失敗`

## 執行記錄（原即時 Log）規格

### 1. 名稱

- UI 顯示名稱統一為 `執行記錄`
- 程式內部類名或 log panel class 名稱不必跟著改

### 2. 訊息分級

執行記錄的使用者可見訊息分成六類：

1. `階段開始`
2. `進度回報`
3. `略過`
4. `警告 / 重試`
5. `失敗`
6. `完成摘要`

每類都要有固定說話方式，不接受英文 debug 殘留。

### 3. 訊息格式

#### 階段開始

- `開始抓取追隨作者：共 128 位`
- `開始掃描作品 PID：待處理 320 位作者`
- `開始整理作品 URL：待處理 420 個 PID`
- `開始下載作品：待處理 860 個 URL`
- `開始查到即下載：待處理 240 個 PID`

#### 進度回報

- `掃描中：作者 12 / 128`
- `整理 URL 中：PID 42 / 420`
- `下載中：PID 123456，第 2 / 5 張`

#### 略過

- `略過 PID 123456：未達最低讚數（18 / 30）`
- `略過 PID 123456：作品沒有 tag`
- `略過本次排程：已有任務執行中`

#### 警告 / 重試

- `注意：目前正在處理 PID 123456，將在此組完成後停止`
- `重試 PID 123456：第 2 / 3 次，原因：Proxy 連線失敗`
- `注意：找不到 cjxl.exe，本次略過 JXL 轉檔`

#### 失敗

- `抓取追隨作者失敗：<原因>`
- `整理作品 URL 失敗：<原因>`
- `下載作品失敗：<原因>`
- `查到即下載失敗：<原因>`

#### 完成摘要

- `抓取追隨作者完成：新增 128 位`
- `整理作品 URL 完成：新增 860 個 URL`
- `下載作品完成：成功 820，略過 30，失敗 10`
- `查到即下載完成：成功 210，略過 20，失敗 10`

### 4. 明確要求移除的現有訊息風格

以下類型不得再直接出現在使用者可見執行記錄中：

- `Task failed`
- `total following: 123`
- `Pending URL: 456`
- `PID progress: 78`
- 缺主詞、缺結果、只剩名詞堆疊的句子

### 5. 顏色語意

- `完成`：success 色
- `失敗`：error 色
- `警告 / 即將停止 / 重試`：warning 色
- `略過 / 補充資訊 / 階段摘要`：secondary / muted 色
- 不再讓一般進度訊息與錯誤訊息使用同樣強度

## 驗收標準

1. 四個主頁面的高可見度標題與主要操作名稱符合本 spec。
2. 設定頁不再沿用舊的 5 區分法，而是採 8 區資訊架構。
3. `Cookies`、`即時 Log`、`統計資料`、`Task failed`、`Pending URL`、`total following` 這類高可見度混語系文案不再出現在使用者可見 GUI。
4. 對話框、Snackbar、狀態標籤和執行記錄的語氣一致，皆採「技術詞保留，但更白話」。
5. 執行記錄至少在「開始 / 略過 / 失敗 / 完成」四類訊息上採固定句型，不再是鬆散的工程輸出。
6. 視覺調整只限於輕量 polish，不改整體畫面架構或功能流程。
7. 這次整理不改設定 key、事件模型、下載流程與統計邏輯。

## 實作建議順序

如果後續要實作，建議順序如下：

1. 先改全域高可見度名稱：
   - 頁面標題
   - 主要按鈕
   - 區塊標題
2. 再改設定頁 8 區結構與欄位文案
3. 再改 Cookie / 統計 / 主頁的輕量排列與資訊權重
4. 最後整理執行記錄訊息，優先清掉混語系與過短 debug 式輸出

這樣可以把風險留在最低，並且讓測試與人工驗收都容易分段進行。
